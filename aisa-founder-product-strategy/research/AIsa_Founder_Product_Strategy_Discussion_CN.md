# 对 AIsa 产品与增长的四点观察

对照 Monid、Orthogonal、Nevermined｜2026-09-04

我围绕四家平台的官网、接入文档、Skills、API 目录与公开传播记录做了对比。我的核心判断是：**AIsa 已经通过统一入口降低了多供应商接入与结算的成本，下一步更值得解决的是：用户和 Agent 如何选对服务，并持续获得可靠结果。**

供给广度是 AIsa 的基础，但供给越多，理解、选择和验收的成本也越高。产品需要一条明确主线，把获客、首次接入、能力发现和质量保障连接起来。

## 一、定位与获客：先明确谁会持续付费，再决定如何被看见

四家平台给我的第一印象，是对“用户为什么要用我”的表达聚焦程度不同。

| 平台 | 对外主线 | 我认为值得借鉴的地方 |
|---|---|---|
| AIsa | 模型、数据 API、Skills、GTM、支付等多个入口 | 资源丰富，但需要明确哪个场景是用户的第一站 |
| Monid | Discover → Inspect → Run | 从“不知道该用什么工具”开始，直接解释使用路径 |
| Orthogonal | Discover → Call → Pay | 用联系人查询等具体示例，让用户快速理解价值 |
| Nevermined | For Agents / For Merchants | 按买方和卖方组织能力，预算授权与收款价值清晰 |

参考：[AIsa](https://aisa.one/)、[Monid 文档](https://docs.monid.ai/)、[Orthogonal](https://www.orthogonal.com/)、[Nevermined](https://nevermined.ai/)。Nevermined 更偏交易基础设施，并非完全同类的工具聚合竞品。

### 我的判断

上面的差异不只是首页表达方式不同：Monid、Orthogonal 先告诉用户如何完成工具发现与调用，Nevermined 先区分谁付钱、谁收钱；AIsa 则同时展示多类资源。用户能看到“平台有什么”，但还需要自己判断“为什么我的任务应该从这里开始”。因此，聚焦入口之前，需要先明确哪类客户最需要这些能力的组合。

AIsa 的统一接入、结算与跨服务组合，在客户反复使用多个供应商时更容易体现价值：只调用一个接口，聚合平台能节省的工作有限；需要持续组合搜索、抓取和分析时，采购、集成与维护的负担才会累积。结合现有数据与 GTM 入口，我会优先验证：**已经在做商业研究、竞品监测或 GTM Agent，需要反复调用多个数据源，但没有专职采购和平台团队的小型公司。** 这是从能力与需求匹配推导出的切入假设，并非认定其他客户不值得服务。

如果优先服务这类自助接入的小团队，获客就需要衔接他们从发现工具、判断适用性到运行示例的过程。Build in Public、社区、搜索与产品发布，应让用户先看到具体任务的实现，再进入对应接入路径。沿着这一逻辑看公开传播，已有 X 快照显示，AIsa 与 Monid 的内容触达存在差距：

### 我的建议

先围绕一个任务形成统一表达，例如“让小团队快速构建有来源、费用可控的商业研究 Agent”。模型路由、数据和支付作为完成任务的支持能力，不必在首页各自争夺主定位。

传播也围绕同一个任务展开：公开 Demo、代码、成本、失败案例与迭代，每次发布链接到对应可运行示例，而不是泛首页。把 Product Hunt 和社区发布组织成一个明确版本的发布，而非只追求曝光。

我的初步 SEO/AEO 测试也感到 AIsa 的可发现性不足。建议从任务型页面入手，提供清晰的输入输出、示例、价格与限制，并用固定搜索词和问答集持续复测。最终看渠道带来多少首次成功和重复付费，而不只看粉丝或排名。

## 二、开发者体验：资源可以丰富，第一次使用必须简单

我的体验是，AIsa 首页同时呈现多类能力，用户需要自己判断模型、API、Skill 和支付之间的关系；文档也存在叙述层级、颗粒度和使用路径不够一致的问题。相比之下，Monid、Orthogonal 的主路径更容易辨认。

这不只是视觉风格问题。用户第一次来到平台，首先想知道“能不能解决我的任务”，而不是先理解平台完整的产品分类。

### 我的判断

当前的信息组织更接近供给目录，而不是用户完成任务的顺序。入口多、文档多，本身不代表体验差；真正的摩擦是用户需要不断自行补齐它们之间的关系。

### 我的建议

首页先回答三个问题：为谁服务、完成什么、怎么开始。保留完整目录，但让首屏聚焦一个价值主张和一个可运行示例。

文档沿同一条路径组织：

**快速开始 → 完成一个任务 → 发现与选择服务 → 执行与排错 → 计费及生产使用 → 完整 API 参考。**

尤其要明确区分“本地 Agent 读取 Skill”“CLI 安装或调用”“云端 API 执行”的职责。我在理解这些关系时需要反复核对文档，这本身就是可改善的接入摩擦。

同一个示例应该贯穿官网、文档、Skill 和调用记录，统一命名、参数与计价单位。优化是否有效，用首次任务成功率、完成时间和求助原因验证，而不是仅以页面是否“极客”判断。

## 三、能力发现：一把 Key 之后，还需要替用户减少选择

AIsa 已有 Agent Card、OpenAPI、MCP manifest 等机器可读入口，因此问题不是“完全没有 discovery”，而是这些能力是否已经进入用户默认使用路径。[Agent Discovery](https://aisa.one/agent-discovery)

单项 Skill 适合把已知任务封装成模板。但如果用户必须先选中并安装某个 Skill，才能让 Agent 使用对应能力，那么发现与选择成本仍主要由人承担。统一 Key 解决了账户问题，还没有自动解决工具选择问题。

### 我的判断

Monid 的 Discover → Inspect → Run 更直接地回答了“不知道该用哪个服务怎么办”。AIsa 可以借鉴这条交互路径，而不是让用户自行从元数据中拼出发现流程。公开提供发现资料，与默认完成发现、比较和执行，是两件事。

### 我的建议

提供一次接入的通用发现入口，让 Agent 从任务出发检索能力；保留单项 Skill 作为成熟工作流模板，也保留直接指定 API 的方式。

先用一个已有多供应商的场景验证，例如网页正文提取。AIsa 目录中有 Tavily Extract、Exa Contents、Firecrawl Scrape，能力存在交集，但输入输出和适用范围并不完全相同。[搜索能力目录](https://aisa.one/api/search)

建议的默认流程是：

**输入任务与预算 → 返回少量候选及限制 → 解释选择理由 → 调用 → 检查结果 → 展示来源与费用。**

第一版不必自动处理整个目录。先让这一类任务的候选检索、费用比较和结果验收成立，验证是否减少人工选工具的次数，并缩短任务完成时间。

探索阶段可以动态选择；生产任务则允许固定已验证的供应商与版本，只在预先批准的范围内切换。发现不应变成每次调用都必须重复支付的成本。

## 四、供应商质量：从“能调用”走向“值得持续使用”

当多个供应商提供相近能力，用户不仅需要知道“有哪些”，还需要知道“为什么选它”。更便宜的请求不一定意味着更便宜的成功结果，HTTP 200 也不代表返回内容可用。

### 我的判断

供给持续扩张后，平台的差异化会越来越依赖选择和质量保障。Orthogonal 将供应商验证与监控作为对外卖点；Nevermined 强调预算授权与交易。这些分别覆盖信任与交易的一部分，但都不能直接替代任务结果验收。

AIsa 的机会，是把选择依据与实际交付数据连接起来，而不是只增加一个未经解释的评分。

### 我的建议

从重点任务建立三层证据：

| 层级 | 应回答的问题 | 关键依据 |
|---|---|---|
| 供应商 | 来源和使用条件是否可信？ | 主体、数据来源、授权与使用限制、故障处理记录 |
| 接口 | 能否稳定执行？ | 成功率、延迟、超时、参数及版本稳定性 |
| 任务 | 返回结果是否有用？ | 完整性、相关性、新鲜度、来源可追溯性与抽检结果 |

先按能力、使用条件和预算过滤，再比较质量、延迟及**单位成功任务总成本**，把重试和二次验证计入成本。推荐理由应附样本量与更新时间，而不是用单一“可信度分数”掩盖未知项。

供给管理形成持续反馈：

**准入测试 → 小规模调用 → 结果验收 → 更新推荐与流量 → 降级隔离、复测或退出。**

给新供应商有限测试机会，避免历史流量固化排名；对不稳定服务及时降级并提供替代路径；将商业推广与质量推荐分开。先在网页提取这样的明确任务上做出可比较的证据，再逐步扩展。

## 我会优先推进什么

我会先把首页、文档和一个任务示例收敛到同一类客户，再把通用发现和最基本的质量记录接入这条路径。Build in Public、SEO/AEO 同步围绕真实示例产出，让传播承诺与实际体验一致。

这个阶段，我不会优先增加更多平行入口，也不会一开始建设覆盖全目录的自动路由系统。判断投入是否成立，主要看四件事：首次任务是否更容易成功、人工选择是否减少、单位成功任务成本是否下降、目标客户是否持续付费且贡献毛利可持续。

**我认为 AIsa 最值得放大的优势，是丰富供给、统一接入与结算，以及跨服务组合能力；需要补强的，是将这些资源组织成一条容易理解、容易接入、可以信任的任务路径。** 如果能够持续证明“选得更省心、完成得更可靠”，平台价值就不只是 API 聚合和价格差。

我希望有机会结合实际客户、调用与留存数据，进一步验证这些判断，并把其中最有价值的部分推进成可交付的产品改进。
